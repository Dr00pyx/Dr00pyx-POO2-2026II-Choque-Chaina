| **1. ¿Qué problema resuelve el principio SRP (S10) en la clase `Estudiante` de la Actividad 2?** | **Problema de Alta Cohesión y Múltiples Razones de Cambio (God Class / God Object):**<br><br>En la Actividad 2, la clase `Estudiante` asume simultáneamente múltiples responsabilidades heterogéneas: *(a)* gestión de atributos e invariantes de identidad (`codigo`, `nombre`, `ppa`, `ciclo`), *(b)* acumulación y mutación del historial de notas, *(c)* lógica de negocio para el cálculo de promedios (`calcular_promedio()`), *(d)* reglas de acreditación académica (`es_aprobado()`), y *(e)* presentación y formateo textual (`to_string()` / `__str__()`).<br><br>El **Principio de Responsabilidad Única (SRP - *Single Responsibility Principle*)** establece que *"un módulo o clase debe tener una y solo una razón para cambiar"*, es decir, responder a un único actor o interés del sistema (Robert C. Martin, 2018).<br><br>Al aplicar SRP en **S10**, desacoplamos estas funciones:<br>1. `Estudiante` se preserva como una entidad de dominio pura encargada exclusivamente de sus invariantes y estado.<br>2. El cálculo de promedios ponderados y reglas académicas se delega al componente de servicio `CalculadorPPA` (apoyado por el patrón GoF Strategy `IEstrategiaCalculo` en S11).<br>3. La persistencia se delega a `IRepositorioEstudiante` (S13), y el renderizado a la interfaz gráfica `GUIEstudiante` (S14).<br><br>Esto evita efectos secundarios no deseados al modificar una regla de negocio o formato de salida sin comprometer la integridad estructural del estudiante. |
| **2. ¿Por qué la GUI (S14) no debe acceder directamente a la base de datos?** | **Violación de Separación de Capas, Acoplamiento Fuerte y Vulnerabilidad de Integridad:**<br><br>Si una interfaz gráfica de usuario (sea desarrollada en Tkinter o PyQt5 en S14) ejecutara consultas SQL directas o interactuara con el almacenamiento físico, surgirían tres problemas críticos:<br><br>1. **Fragilidad ante cambios de persistencia:** Cualquier modificación en el motor de base de datos (por ejemplo, migrar de SQLite a PostgreSQL o cambiar los nombres de columnas o esquemas) forzaría a reescribir la capa visual, lo cual rompe el principio de diseño en capas (*Layered Architecture*).<br>2. **Duplicación de lógica de negocio (Spaghetti Code):** Si existen múltiples vistas (por ejemplo, formulario de matrícula de escritorio en PyQt5, consola CLI o futura API Web), las validaciones y reglas académicas tendrían que reescribirse en cada vista, provocando inconsistencias cuando una de ellas no se actualice de forma sincrónica.<br>3. **Seguridad, transaccionalidad y auditoría:** La capa de servicios (`ServicioEstudiante` / `ServicioMatricula`) actúa como una frontera de seguridad (*Boundary Layer*), administrando transacciones atómicas, logs, validación de precondiciones y notificaciones automáticas (como el `NotificadorEmail` mediante el patrón Observer en S12). La GUI solo debe enviar comandos/eventos y renderizar datos proyectados (*DTOs/ViewModels*). |
| **3. ¿Qué ventaja tiene `IRepositorioEstudiante` sobre una clase concreta `RepositorioJSON`?** | **Inversión de Dependencias (DIP) e Intercambiabilidad Polimórfica (Patrón Repository):**<br><br>Según el **Principio de Inversión de Dependencias (DIP - *Dependency Inversion Principle*, S10)**, los módulos de alto nivel (como la capa de lógica de negocio `ServicioEstudiante`) no deben depender de implementaciones concretas de bajo nivel (como un archivo JSON o una base de datos específica), sino de una abstracción (`interface IRepositorioEstudiante`).<br><br>Ventajas determinantes:<br>1. **Principio Abierto/Cerrado (OCP):** El sistema puede incorporar nuevos motores de persistencia (`RepositorioSQLite` en S13, `RepositorioSA` con SQLAlchemy en S15, o almacenamiento en la nube) implementando la misma interfaz sin tener que alterar ni una sola línea de código en `ServicioEstudiante`.<br>2. **Testabilidad Inmediata (*Unit Testing & Mocking* en S17):** Para probar los servicios en `pytest` no es necesario escribir ni leer archivos en disco; basta con suministrar un `RepositorioMemoriaMock` que implemente `IRepositorioEstudiante`, logrando pruebas unitarias ultra rápidas, deterministas y aisladas del entorno del sistema operativo. |
| **4. ¿Cuándo tiene sentido llamar código C++ desde Python con `ctypes` (S16)?** | **Optimización de Rendimiento en Procesamiento Intensivo (CPU-bound) y Reutilización de Motores Nativos:**<br><br>Python destaca por su rapidez de desarrollo, legibilidad y rico ecosistema de GUI y librerías, pero posee desventajas inherentes de velocidad al ser un lenguaje interpretado con tipado dinámico y presencia del *Global Interpreter Lock* (GIL), lo que limita el paralelismo nativo en cálculos matemáticos masivos.<br><br>Tiene pleno sentido recurrir a `ctypes` (o Cython / pybind11) para invocar `libcalculo.so` o `calculo.dll` en C++17 en los siguientes escenarios:<br>1. **Cálculos numéricos pesados (CPU-bound):** Algoritmos de promedios ponderados a gran escala sobre decenas de miles de registros históricos de alumnos, simulaciones de egreso, rankings de rendimiento o modelos probabilísticos que aprovechan optimizaciones de compilador (`-O3`, vectorización SIMD AVX-512).<br>2. **Reutilización de activos de software existentes (*Legacy Code*):** Si la universidad ya cuenta con motores de cálculo aprobados y certificados escritos en C/C++, resulta más seguro y económico enlazarlos mediante interfaces binarias `extern "C"` que reescribirlos desde cero en Python.<br>3. **Arquitectura híbrida óptima:** Permite utilizar Python como "pegamento" de alto nivel para interfaz visual, persistencia y orquestación, delegando las tareas de fuerza bruta al motor compilado en C++. |
| **5. ¿Qué problema detectaría `pytest` (S17) si cambias la firma de `calcular_promedio()`?** | **Regresiones de Contrato, Ruptura de API y Errores en Tiempo de Ejecución (*Runtime Failures*):**<br><br>En lenguajes de tipado dinámico como Python, un cambio en la firma de un método no genera errores en tiempo de compilación. Por ejemplo, si `calcular_promedio()` se renombra a `calcular_promedio_semestre()`, si se le agrega un argumento posicional obligatorio sin valor predeterminado como `calcular_promedio(estrategia)`, o si el valor de retorno cambia de `Optional[float]` a una estructura tupla `(promedio, estado)`:<br><br>1. **Detección temprana de rotura de contrato:** `pytest` ejecutará inmediatamente las pruebas unitarias y suites de integración que consumen dicho método. Al detectar un `TypeError: missing required argument`, `AttributeError: object has no attribute 'calcular_promedio'` o una falla en `assert`, la suite fallará en segundos indicando con precisión el archivo, la función y la línea exacta donde se produjo la incompatibilidad.<br>2. **Prevención de fallos silenciosos en producción:** Sin pruebas automatizadas con `pytest`, este defecto solo se manifestaría cuando el usuario final interactúe con el botón de "Calcular Promedio" en la GUI (S14) en pleno uso por la administración académica, produciendo un crash inesperado del sistema.<br>3. **Soporte para Refactorización Continua (*Refactoring Confidence*):** Proporciona una red de seguridad (*safety net*) indispensable para avanzar en los patrones de diseño GoF y SOLID a lo largo de las semanas S10 a S18. |

- **S18:** Consolidación, integración continua y entrega final del sistema académico.
